How a GitMesh project works

A GitMesh project is one folder. Some directories inside it are separate Git repositories (marked repo below); everything else belongs to the root repository. GitMesh shows them as one project, so you commit, pull and push once. Each repository still gets its own real Git commit, and Git itself makes every change.

Repositories of this project

A repository boundary is configuration. GitMesh changes one only after you reviewed the plan and the manifest text it writes; files, .git directories, history and remotes are never touched by a configuration change.

Add a directory as a repository

GitMesh checks the directory first and tells you exactly what it would do: adopt an existing repository, create one, record a remote, or refuse.

Change one repository

Removing a repository is a configuration change: its directory, its .git, its history and its remote stay exactly where they are. Renaming changes the name in GitMesh, never the directory.

Operation

No GitMesh project is open

A GitMesh project is any directory tree containing .gitmesh/project.toml.

The setup wizard scans the directory, lets you choose which parts become repositories, shows you the exact plan, and writes the manifest — nothing is deleted and nothing is replaced without confirmation.

Set up a GitMesh project

Every step is shown as GitMesh sees it, and the review step shows the real plan — the same plan that runs when you confirm it. Nothing is deleted, no .git directory is re-initialised, no remote is replaced and no manifest is overwritten without an explicit confirmation.

1 Project root

The directory that becomes the logical project. Absolute path; it may already contain files, and it may already be a Git repository.

2 Structure

GitMesh reads the directory as one project. Tick the sub-directories that should be their own Git repository (for hosting, collaboration or size); everything else stays part of the root repository. A nested repository is reported, never touched.

3 Root repository

The root repository holds the project files that no other repository owns. GitMesh creates it when needed: you never run git init yourself.

4 Repositories inside the project

One row per selected directory: its name in the project, whether GitMesh creates the repository, and where it is hosted. Defaults are suggestions, never decisions.

5 Repositories that already exist

A directory that already is a Git repository is used as it is: GitMesh never converts, re-initialises or deletes it. Adopting it records it in the manifest; keeping its remote is the default and its history stays untouched.

6 Remotes

A remote is optional: a project with no remote is fully usable locally. The URL is always recorded in the manifest; configuring origin in Git as well is a separate choice.

7 Hosting (optional)

GitHub is optional and never required. GitMesh does not create repositories on GitHub, needs no token and stores no credential: it prepares the correct remote URL and tells you the command that creates the repository there, if you want one.

8 Manifest

GitMesh writes .gitmesh/project.toml from these answers, using the project schema and its validation. You never edit TOML by hand.

9 Review and dry run

This is the real plan: exactly what GitMesh will create, keep, skip or refuse. It is generated from the answers above and nothing runs until you confirm it.

10 Confirm

The plan id below is the exact plan you reviewed. If anything in the directory changes in the meantime, GitMesh refuses to run it and asks you to review again.
